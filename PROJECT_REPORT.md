# Project Report: Business Knowledge AI Bot

## 1. Problem
General-purpose LLMs do not reliably know the facts of a specific company and can present invented details confidently. A company assistant needs answers grounded in the company's own documents.

## 2. Objective
Build a small, understandable RAG application that answers questions from a local Markdown knowledge base, cites the source files it used, and refuses to answer when the documents do not contain the information.

## 3. Architecture
Documents → loader → cleaning → chunking → TF-IDF vectors (scikit-learn) → local index (`kb_index.joblib`) → cosine similarity retrieval (top-K) → relevance check → local Python answer generation → Gradio interface. It runs fully offline with no AI API or API key. Three scripts implement it: `ingest.py` (build the local index), `answer.py` (retrieve and generate), `app.py` (interface).

## 4. Document ingestion
All `.md` files in `knowledge-base/` are loaded. Each document carries `source` (filename) and `category` (filename without extension, e.g. `local-offices`) metadata. The database is deleted and rebuilt on every run so it always mirrors the current files; this keeps behaviour simple and prevents duplicate records.

## 5. Cleaning
Cleaning removes HTML comments (the template instructions), normalises line endings and non-breaking spaces, trims trailing and repeated spaces, and collapses long runs of blank lines. Markdown headings are kept. Files with no content after cleaning are skipped with a warning.

## 6. Chunking
A recursive character splitter creates chunks of 800 characters with 150 characters of overlap (both configurable). Chunks are small enough to give focused matches and large enough to keep context; the overlap prevents ideas being cut at boundaries. Splitting prefers headings, then paragraphs, lines and words. Each chunk gets a `chunk_id`.

## 7. Vectorisation (TF-IDF)
Chunks and questions are converted into TF-IDF vectors with scikit-learn using the same fitted vocabulary, so both live in the same vector space. TF-IDF weights rare, meaningful words highly and common words lightly. No embeddings API is used; everything is computed locally.

## 8. Local retrieval
The TF-IDF matrix and chunk metadata are saved to a single local file (`kb_index.joblib`). For each question, cosine similarity ranks all chunks and the top-K (default 4) are retrieved with their similarity scores. A configurable `SIMILARITY_THRESHOLD` decides whether a chunk is relevant enough to use; if none qualify, the bot returns the fallback instead of guessing.

## 9. Answer generation (local, extractive)
Chunks that pass the relevance threshold are turned into an answer in plain Python — no language model. The chunks are split into sentences, the sentences that overlap most with the question's words are selected (verbatim from the documents, so nothing is invented), and they are stitched into one concise, grounded paragraph. Because the text is taken directly from the knowledge base, answers cannot hallucinate company facts.

## 10. Persona and conversational replies
The assistant is presented as a friendly, professional knowledge assistant that is not an official company representative. Simple greetings ("hi") and thanks are answered with short canned replies in Python, and empty input asks the user to type a question — none of which touch the knowledge base.

## 11. Fallback
Invented answers are prevented structurally. If no retrieved chunk reaches `SIMILARITY_THRESHOLD`, the application returns a fixed "I don't know based on the company documents I have available" message. Because answers are built only from retrieved chunk text (extractive) rather than generated by a language model, the bot cannot fabricate company facts in the first place.

## 12. Design choices
Plain Python and a handful of well-known libraries (scikit-learn, joblib, Gradio); no external AI API, no API key, no agents or extra infrastructure. Optional settings live in `.env`. Errors (missing index, empty question) return readable messages instead of stack traces. Retrieved chunks and their similarity scores are shown in the UI to make the retrieval process visible.

## 13. Limitations
The bot only knows what is in the knowledge base, and retrieval quality depends on document quality. The similarity threshold is a heuristic that may need tuning per knowledge base. Answers are extractive (assembled from source sentences), so they read as concise quoted facts rather than free-flowing prose. There is no live website sync and no authentication. It is a prototype.

## 14. Future improvements
Automatic synchronization, document versioning, hybrid search, reranking, better citations, authentication, evaluation datasets and production deployment.

## 15. Conclusion
The project demonstrates a complete, readable RAG pipeline with source visibility and a firm "I don't know" behaviour, suitable as a prototype and as a base for a larger knowledge assistant.
